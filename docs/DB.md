# The table the service writes

PostgreSQL holds a single table, a log with one row per scored request. The code inserts rows
and never updates or deletes them. The log records who was scored, and the drift report reads it
to compare recent applicants with those the model learned from.

## `predictions`

| Column | Type | Null | What it holds |
|---|---|---|---|
| `id` | `varchar(36)` | no | a UUID, generated by the application |
| `created_at` | `timestamp` | no | when the row was written, in UTC, indexed |
| `request_id` | `varchar(64)` | no | the request id of the response header, followed by `:<index>` for each row of a batch, indexed |
| `sk_id_curr` | `integer` | yes | the caller's own identifier for the applicant |
| `model_name` | `varchar(255)` | no | the name of the model that was serving |
| `model_version` | `varchar(64)` | no | its version |
| `threshold` | `double` | no | the operating point that turned the score into a decision |
| `proba_default` | `double` | **yes** | the score, when there was one |
| `decision` | `integer` | **yes** | 0 accepted, 1 refused, when there was one |
| `latency_ms` | `double` | no | the time spent building the input frame and scoring it, divided by the number of rows for a batch |
| `status_code` | `integer` | no | the status code the caller received |
| `error_message` | `text` | yes | the failure, in words |
| `failure_kind` | `varchar(32)` | yes | the failure, from a closed vocabulary, indexed |
| `input_payload` | `jsonb` | no | the validated request |
| `output_payload` | `jsonb` | no | the response returned, or an empty object after a failure |

## Four design decisions in this table

**The threshold is stored with the score.** The threshold can change from one model version to
the next, so each row keeps the operating point that turned its score into a decision.

**The score and the decision are nullable.** `credexp.db.models` explains how a zero written in
their place would distort every average computed from this table. `tests/unit/db/test_crud.py`
checks that the row built for a failed request leaves both fields empty.

**A failure has a kind as well as a message.** `failure_kind` takes its values from a closed
vocabulary, so failures can be counted, and `error_message` describes each one in prose.

**The payload is stored whole, as JSON.** `credexp.db.crud` explains why a projection onto the
columns that exist today would lose information. The drift monitor depends on this, because it
reads `input_payload` and none of the engineered columns.

## How the table is created, and what happens without a database

`scripts/init_db.py` and the startup of the application both call `Base.metadata.create_all`,
which creates the table only if it is missing.

Writing to the log is best effort. When the database does not answer, the service writes a
warning to its own log and still returns the score. Opening a connection has a three-second
deadline, set by `DB_CONNECT_TIMEOUT`, and `credexp.db.session` explains what the absence of a
deadline used to cost. `tests/system/test_service_end_to_end.py` points the service at a closed
port and asks it to score.

## What reads it

- `src/credexp/app/prediction_log.py`, for the decision log page, reads the last 200 rows, most
  recent first. The query is bounded because the table grows with every request.
- `src/credexp/monitoring/drift.py`, for the drift comparison, reads `input_payload` from the
  most recent successful requests. These are the requests as the schema validated them, before
  the pipeline imputes the missing columns.
